# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Merged WordPress plugin combining the former standalone `wpconnectorendpoint` and `wpconnectorhub` plugins. One install, three modes stored in the `wpc_mode` option (`endpoint` / `hub` / `both`, `''` before setup): the endpoint module exposes the key-protected `/wp-json/wpconnector/v1/status` REST route on monitored sites; the hub module is the dashboard on the main site that pulls status from a list of those endpoints.

## Structure

- `wpconnector.php` — plugin header plus a PHP 5.2-parseable loader: it checks `version_compare(PHP_VERSION, '7.0', '<')` and, on old PHP, shows an admin notice and bails instead of fataling (old WP cores ignore the `Requires PHP` header and activate anyway). This file must stay free of type declarations, closures and short array syntax. When the check passes it defines the `WPC_*` constants and requires `includes/main.php`.
- `includes/main.php` — the `wpc_` layer (PHP 7.0+ safe from here on): mode option helpers (`wpc_get_mode()`/`wpc_mode_has()`), activation hook (sets the `wpc_setup_redirect` flag when no mode is chosen and ensures the endpoint secret key when one is), one-time redirect to the setup screen, the Settings > WP Connector page (mode radios, POST handled on `admin_init` before output), the "no mode chosen yet" admin notice, plugin-row action link, the plugin-wide update checker (PUC from top-level `plugin-update-checker/`, pointed at the public GitHub repo `github.com/kostasntamas/wpconnector`, branch `main`; no auth needed, with a `WPC_GITHUB_TOKEN` wp-config constant as an override if the repo ever goes private — runs in every mode so endpoint-only sites update too), and finally conditional `require` of the modules. If a standalone plugin is still active (`wpc_legacy_plugin_active()`, matched by file basename so renamed folders are caught), the corresponding module is skipped with an admin notice instead of fataling on redeclared functions/classes.
- `modules/endpoint/endpoint.php` — endpoint module bootstrap: defines `WPCE_PLUGIN_DIR`, requires the `includes/` classes and inits `WPCE_Plugin`. The module is class-based (mirroring the hub's layout): `WPCE_Plugin` wires the hooks, `WPCE_Settings_Page` is the Settings > WP Connector Endpoint page, `WPCE_Rest_Controller` registers three key-protected routes: `/wp-json/wpconnector/v1/status` (the small, frequently-polled payload, including `core_auto_update_policy()`), `/wp-json/wpconnector/v1/plugins` (the per-plugin list, requested only when a hub dialog is opened — see Plugin lists) and `/wp-json/wpconnector/v1/users` (the account list, same on-demand footing — see User lists and account flags; `WPCE_User_Audit` in `includes/class-wpce-user-audit.php` is where all of it lives). Neither callback ever blocks on api.wordpress.org: `update_data()` reads the `update_core`/`update_plugins` transients and, when one is missing, queues core's own `wp_version_check`/`wp_update_plugins` cron hook instead of calling it inline (that inline call used to cost the hub several seconds *per site*). Unknowable fields then come back as `null` rather than a guess — `wp_update_available`/`wp_latest_version` (the hub shows "Not checked yet") and a plugin's `on_wordpress_org` (the hub omits the Free/Premium badge). The `wpce_secret_key` option and page slug are unchanged from the standalone plugin; key generation lives in `wpc_ensure_endpoint_key()` in the main file (called on activation and whenever an endpoint mode is saved).
- `modules/hub/hub.php` — hub bootstrap. Defines the `WPCH_*` constants the class files rely on: `WPCH_PLUGIN_DIR`/`WPCH_PLUGIN_URL` point at `modules/hub/` (so requires and asset enqueues resolve), `WPCH_PLUGIN_FILE` is the merged plugin's main file, `WPCH_VERSION` mirrors `WPC_VERSION`. Then requires the `includes/` classes and inits `WPCH_Plugin`, exactly like the old `wpconnectorhub.php`.
- `modules/hub/includes|assets` — from the standalone hub, with two exceptions: the update checker was removed from `class-wpch-plugin.php` and moved to `wpconnector.php` (see above) so it runs in every mode, with the PUC library relocated to the top-level `plugin-update-checker/`; and the old `includes/functions.php` is gone — `initials()` is now a private static method on `WPCH_Admin_Page`. `includes/class-wpch-prewarm.php` is new (see Status fetching and caching). See the standalone hub's CLAUDE.md for the full description of the hub internals — everything there still applies.

## Comments

Per-site comments are a chat thread stored in each endpoint's `comments` array — plain-text entries `{id, parent, author_id, author, time, text}` where `parent` is `''` for a top-level message or the id of the top-level message it replies to (one level of nesting; replying to a reply re-parents to its top-level message, deleting a top-level message cascades to its replies, and users can only delete their own messages). The row's comment button toggles a popover anchored next to it (`modules/hub/assets/js/comments.js`, Popover API). Thread HTML always renders server-side (`WPCH_Admin_Page::render_comments()`) and the client swaps the container's innerHTML wholesale: on open and message add/delete via the `wpch_comment_fetch|add|delete` AJAX actions, and — while a popover is open — from fast Heartbeat ticks (`WPCH_Comment_Sync`, which replaced the old advisory `WPCH_Comment_Locks`; append-only chat has no overwrite conflicts to lock against). A `comments_rev()` hash guards against redundant swaps, and a swap is skipped while a reply composer inside the thread holds an unsent draft. Pre-2.2 single rich-text comments (`comment`/`comment_author`/`comment_updated`, lilac-editor HTML — the vendored editor is gone) are migrated to plain text as the thread's first message on read in `WPCH_Endpoints::get_all()`, and likewise on JSON import of old export files.

## Status fetching and caching

Opening the hub never blocks on the network. `render_settings_page()` calls `WPCH_Status_Checker::cached_statuses()`, which only reads the cache: a site with no fresh entry comes back as `null` — a third status state alongside payload-array and `WP_Error` (a switched-off row is the fourth, `false`; see the `monitored` note below) — and renders as a dimmed "Checking…" row carrying `data-pending="1"` (it also sits outside every health tier, so the tab bar shows a disabled "Checking N" pill until the sites land). On `DOMContentLoaded`, `admin.js` collects those pending indexes and runs them through `wpchRunBatchedRefresh()` — the same sequential batches of `WPCH_REFRESH_BATCH_SIZE` (8, matching `WPCH_Status_Checker::BATCH_SIZE`) that the global Refresh button uses, with the button doubling as the "Checking X of Y…" progress readout. The sweep passes `silent` so a failed batch logs instead of raising an alert. Consequently `wpch_refresh_statuses` reads its *untargeted* sites via `cached_statuses()` too (they exist only so the health tabs can regroup) — otherwise one batch of 8 would drag every other site onto the wire.

The cache is the non-autoloaded `wpch_status_cache` **option**, not a transient: a transient's single expiry wiped every site's entry at once, so one quiet window meant the next visitor paid for a fully cold fetch. Freshness is now per entry, from its own `fetched_at` against `cache_ttl()` (default 900s, `WPCH_STATUS_CACHE_TTL` in wp-config.php, 0 disables). `cached_entry()` is the one place that decides whether an entry is usable (id present, `url|key` hash unchanged, inside the TTL); an entry's payload is under `data` (`status` is the same thing under its pre-2.3.7 name, still read so an upgrade doesn't discard a warm cache).

`fetch_statuses()`, `fetch_plugins()` and `fetch_users()` are thin wrappers over one private `fetch($endpoints, $kind, $force)` — same batching, SSL hooks, retry pass and timing metadata; `$kind` (`status`/`plugins`/`users`) only picks the URL, the cache option and TTL (`cache_for()`), and how the decoded body is unwrapped.

## Plugin lists

The per-plugin list is **not** part of the status payload. It lives on the endpoint's own `/wp-json/wpconnector/v1/plugins` route (same key check) and in the hub's separate non-autoloaded `wpch_plugins_cache` option, on a much longer TTL (`plugins_cache_ttl()`, default 1h, `WPCH_PLUGINS_CACHE_TTL`) — what a site has installed changes far less often than whether it is up. The status payload keeps only `plugins_total/active/inactive/auto_update/auto_update_supported`, which is what the table cell shows.

Nothing renders a plugin list into the page. `render_plugins_cell()` prints the counts and a button calling `wpchOpenPlugins(index, label)`, which builds a `<dialog>` client-side (appended to `#wpch-dialogs`, so rows swapped in by AJAX work too) and fills it once from `wpch_fetch_plugins` → `render_plugins_list()`. The main table row and that endpoint's health-tab row pass the same index, so they share one dialog — previously each rendered its own full copy of the list into the HTML. The sidebar's All Plugins dialog is the same pattern: an empty shell plus `wpchLoadAllPlugins()` → `wpch_fetch_all_plugins` → `render_all_plugins_grid()`, aggregated across every site's cached list.

Endpoints before 2.3.7 still send `plugins` inside the status payload and have no `/plugins` route. `fetch()` handles that transparently: it moves the list out of the status payload into the plugins cache (`$stashed_plugins`), so those sites' dialogs work without ever calling the route, and a failed plugins fetch falls back to a stale cached list (hash permitting) rather than erroring.

`WPCH_Prewarm` keeps those caches warm: a cron event (`wpch_prewarm_statuses`) force-fetches every endpoint's status on its own schedule — default 600s, i.e. comfortably inside the TTL — so a human normally finds every entry fresh and there is nothing pending at all. It then refreshes plugin and user lists *without* `$force`, so only the ones that have actually aged out go to the network. It self-schedules on `init`, holds a `wpch_prewarm_running` transient so a slow sweep can't have a second one pile onto it, and calls `prune_cache()` afterwards (which cleans both caches) (it is the only caller that always sees the complete endpoint list, so it is also where deleted endpoints' entries and the pre-2.3.6 transient get cleared). `WPCH_PREWARM_INTERVAL` / `WPCH_PREWARM_DISABLED` in wp-config.php override it. The event is cleared by hook name from `wpc_deactivate()` and from the mode-save handler when the new mode drops the hub — the module wouldn't be loaded to unschedule itself.

## User lists and account flags

Same split as the plugin lists, for the same reasons plus one more: no name or email address travels on the polled route. The status payload carries only `users_total`, `users_admins`, `users_flagged` and `users_high`; the list itself is on the endpoint's `/wp-json/wpconnector/v1/users` route and in the hub's `wpch_users_cache` option (`users_cache_ttl()`, default 1h, `WPCH_USERS_CACHE_TTL`). `render_users_cell()` prints total/admin counts, a `⚠ N` indicator (amber, or red when `users_high` is non-zero) and a View Users button calling `wpchOpenUsers(index, label)` — which goes through the same `wpchOpenList()` helper as `wpchOpenPlugins()` (one lazily-built `<dialog>` per kind per row index) into `wpch_fetch_users` → `render_users_list()`. Endpoints before 2.3.9 have no `/users` route and no `users_*` fields: the cell renders an em dash (not a zero) and the dialog explains that the endpoint needs updating.

`WPCE_User_Audit` on the endpoint side owns both the counts and the per-account grading. There is no clean way to decide that an address *is* a phishing address — what it checks is whether an address is real and whether the account around it looks like one an intruder left behind. Each signal has a weight: throwaway mailbox provider, punycode/homoglyph mail domain, a domain within levenshtein 2 of the site's own, a domain with no MX **and** no A record (the one objective test, `checkdnsrr`), an administrator created within `RECENT_DAYS`, administrator capabilities with no role at all, a role the site doesn't define, and a machine-looking username. The sum plus one for privileged accounts (only once the score is already ≥ 2, so a single soft flag stays mild) becomes `none` / `watch` / `high`, which the dialog renders as amber "Worth checking" or red "Possibly compromised". They are warning signs, never verdicts, and the UI says so.

Cost control on that route: `summary()` is capped (`MAX_SCAN`, privileged accounts plus recent registrations only — never a full user table walk) and cached in the `wpce_user_summary` transient for 5 minutes; `users()` is capped at `MAX_USERS` with privileged accounts selected first. DNS runs **only** in `users()` (results cached in the `wpce_user_audit_dns` transient, 12h; `WPCE_USER_AUDIT_DNS` disables it) — a slow resolver must never hold up the polled status route, and an unavailable one answers "deliverable" so a blocked resolver can't turn every account red. The consequence is that `users_high` can grade an account milder than the dialog does; the account is still counted in `users_flagged`, and opening the list is what runs the full check.

## Health grading

`WPCH_Status_Checker::wp_status()` grades a site by its gap to the latest WordPress feature release (X.Y): up to `MAX_HEALTHY_WP_GAP` (3) releases behind — including a missing maintenance/security release within the same X.Y branch — the tier stays `good`, so the site still shows as Healthy (PHP permitting). More than 3 releases behind (or an older first version number, "Very old") is `deprecated`, which puts the site in the Needs Attention tab. PHP grading (`php_status()`) is unchanged and can still pull a site down to Fair (`aging`) or Needs Attention (`deprecated`) on its own.

## Conventions

- Short array syntax (`[]`) everywhere in `includes/main.php` and `modules/` — the vendored `plugin-update-checker/` library is left untouched, and the `wpconnector.php` loader is the deliberate exception (see above).
- Parameter and return types on functions/methods, PHP 7.0-compatible only (hub and endpoint alike): no `void` or nullable `?type` hints (7.1+), no typed properties (7.4+) — properties carry a `/** @var Type */` docblock instead, and nullable params/returns stay untyped with a comment (also avoids the PHP 8.4 implicit-nullable deprecation). Values that can be array-or-`WP_Error` (endpoint statuses) stay untyped with a comment too.
- Both modules are class-based; the `wpc_` layer in `wpconnector.php` stays procedural (it runs before any module loads).

## Notes

- Same option names as the standalone plugins (`wpce_secret_key`, `wpch_endpoints_list`, `wpch_folders`, ...), so data migrates automatically in both directions.
- Switching modes never deletes data — an unloaded module's options stay in the DB.
- Each endpoint may carry a `login_url` override (`''` = the default `<base>/wp-admin/`), resolved via `WPCH_Endpoints::login_url_for()`; it's set from the Add form (`new_login_url`) or the row's edit dialog (`edit_login_url`), normalized by `normalize_login_url()` (a bare path like `/wp-admin/` is resolved against the site's base URL), and survives JSON export/import.
- Each endpoint may be switched off for sites that aren't WordPress (another CMS, a static site): `WPCH_Endpoints::is_monitored()` reads the row's `monitored` field (1/0, missing = monitored, so pre-existing rows and older exports are unaffected). Set from the Add form's `new_unmonitored` checkbox or the row's edit dialog (`edit_unmonitored`, sent as an explicit `'1'`/`'0'` so older cached JS can't silently re-enable a row). Both `cached_statuses()` and `fetch()` short-circuit such a row to `false` — a fourth status state next to payload-array / `WP_Error` / `null`-pending — so nothing ever requests it: not a page load, not the Refresh button, not the prewarm cron, and not the plugin-list routes. The row renders dimmed (`wpch-row-off`) with a "Not monitored" health cell and **no** `.refresh-row` button, which is what keeps it out of the client's batch sweeps (`wpchRowIndexes('.refresh-row')`); it belongs to no health tier and is counted on its own disabled "Not monitored N" pill in the tab bar.
- The hub page layout is a thin dark sidebar (`.wpch-sidebar`: brand, an Add Site button and the Backup export/import actions — Add and Import open `<dialog>`s, `#wpch-add-dialog` keeping the `#wpch-add-form` id admin.js submits via AJAX) plus a sticky top bar (`.wpch-topbar`: the search bar `#wpch-search-btn` that opens the Ctrl+K palette, the current user's initials chip, and Logout). The table `thead` sticks below the top bar via `--wpch-topbar-h`.
- Ctrl+K (or the search bar in the top bar) opens a non-modal palette (`#wpch-search` in `render_settings_page()`, logic in `admin.js`) that live-filters the main table by the rows' `data-domain` attribute only — keys/tags/comments are never matched. Hiding is a `wpch-search-miss` class (rows and emptied folder groups); collapsed folders holding a match are force-opened by flipping their toggle checkbox programmatically (no change event, so the temporary state is never persisted) and folded back when the filters clear — unless the user toggled them manually meanwhile. Enter keeps the filter, Esc clears it, and `wpchRenumberRows()` re-applies the active filters after row swaps.
- Three select filters above the main table (`.wpch-filters`, rendered in the `data-tab="all"` panel) combine with the Ctrl+K query — a row must pass all active criteria (`wpchApplyFilters()` in `admin.js`, matching the rows' `data-tag`/`data-wp`/`data-php` attributes). Tag options are the fixed `tag_presets()` (plus `__none__` = untagged); the WP/PHP version options are rebuilt from the versions currently in the table (`wpchRebuildVersionFilterOptions()`, newest first) on load and after every row swap, dropping a selected version that disappeared. Offline rows carry empty version attributes, so any version filter hides them.
- The Offline tier panel is the one health tab with actions: each row carries the endpoint's edit button and a re-check button (`.refresh-row` with the same `data-index`), because a site is usually there for a wrong/missing key or URL. The edit button calls `wpchOpenEndpointEdit()` rather than `commandfor`, because switching tabs puts `hidden` on the whole main-table panel and a `<dialog>` under `display:none` opens invisible — it moves the row's one dialog into `#wpch-dialogs` (outside every panel) first, and `wpchDropRelocatedEditDialog()` discards it wherever a row is re-rendered so the id never doubles up. For the same reason `send_row()` returns `health_tabs` alongside `row_html`: an edit launched from the Offline tab has to be able to take the site out of it. Both batch sweeps scope their selector to `#wpch-status-table .refresh-row` so these buttons aren't collected twice.
- The `wpch_refresh_statuses` AJAX action takes an optional `index` (the per-row refresh icon) or `indexes` (a batch from the Refresh button or the on-load pending sweep): the named sites are force-fetched and returned in `rows`, while the other statuses come from cache so the health tabs can still regroup. With neither, everything is force-fetched.
- Requires PHP 7.0+ — avoid 7.1+-only syntax in all module code (see Conventions).
- The GitHub repo referenced by the update checker must have version tags (or a higher `Version:` header on the `main` branch) before updates will be offered; until then PUC simply finds no updates.
